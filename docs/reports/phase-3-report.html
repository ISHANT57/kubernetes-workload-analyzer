1. What Phase 3 was for

Phases 1-2 built the data layer (cluster, monitoring stack, verified metrics) and the demo fixtures. Phase 3 built the backend's skeleton: configuration, the Prometheus and Kubernetes clients, the analysis loop, and the operational HTTP surface (/healthz//readyz//metrics//api/runs/latest). Deliberately out of scope for Phase 3: the rule engine, evidence builder, cost model and /api/findings — those are Phase 4. The done-condition (PHASES.md): "Runs against the cluster; degrades cleanly with Prometheus down."

2. Package layout

Go 1.27 module under backend/, chosen and recorded as D-001. Every external call sits behind a small interface so the whole module except cmd/* is testable with fakes, no live cluster required (backend/README.md).

cmd/analyzer/main.go        wiring only: config -> clients -> runner -> http server
internal/config/            env-var configuration, validated
internal/logging/           structured JSON logging (stdlib log/slog)
internal/model/             dependency-free domain types (AnalysisRun, WorkloadRef, ...)
internal/promclient/        Prometheus client behind an interface (instant + range queries)
internal/k8sclient/         Kubernetes client behind an interface, scoped to D-007
internal/runner/            the analysis loop: timer, failure handling, in-memory snapshot
internal/httpserver/        /healthz /readyz /metrics /api/runs/latest
internal/metrics/           the analyzer's own Prometheus metrics (self-observability)

3. The analysis loop design

An in-process ticker runs on ANALYSIS_INTERVAL, lists workloads from the Kubernetes API, and keeps the latest result as an in-memory snapshot (internal/runner) — no queue, no worker process, no database (docs/architecture.md, "Shape: modular monolith"). Each cycle produces a model.AnalysisRun with a status of complete, partial or failed. On a source failure, the runner keeps the previous snapshot rather than blanking it — the sticky-snapshot pattern used consistently in every later phase too (findings in Phase 4, the dashboard's polling hook in Phase 5).

4. Kubernetes and Prometheus clients (D-007 scope)

internal/k8sclient lists namespaces, nodes, deployments, replicasets, statefulsets, daemonsets, HPAs and events only — the read-only ClusterRole decided in D-007. No pods, secrets or configmaps access exists in the client at all, not just in the RBAC that constrains it: a coding mistake could not accidentally list pods even before the in-cluster RBAC is applied (that live RBAC verification is Phase 7). internal/promclient wraps client_golang/api/prometheus/v1 for instant and range queries, with per-query timeouts.

7. Live verification against the real cluster

Run with the real kind cluster and a real Prometheus port-forward, not just against fakes:

Results (2026-09-25):
  • Correctly counted 16 deployments from the live Kubernetes API on the first run.
  • Prometheus access was killed mid-run and restored live: /readyz correctly went 503 during the outage and recovered to 200 once Prometheus was reachable again.
  • workloads_seen stayed at 16 throughout the outage — carried forward from the last successful Kubernetes listing, never dropped to 0 by a Prometheus failure (Kubernetes and Prometheus are independent sources; one failing does not blank the other's last-good data).
  • /healthz stayed unaffected the whole time (process liveness, not dependency health).
  • Graceful SIGTERM shutdown confirmed: the process drains and exits cleanly, not killed mid-request.

8. Graceful shutdown

cmd/analyzer/main.go listens for SIGTERM/SIGINT and shuts the HTTP server down with a bounded context, rather than the process dying mid-request — the behaviour a Kubernetes Deployment rollout or kubectl delete pod relies on to avoid a dropped request. Verified locally (§7); re-verified in-cluster during Phase 7's rollout.
