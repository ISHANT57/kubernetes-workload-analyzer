1. What Phase 1 was for

The project builds an analyzer that turns Kubernetes and Prometheus data into evidence-based findings (for example "this workload requests far more CPU than it uses"). Phase 1 did not write analyzer code. It had two jobs:

  1. Learn the Kubernetes behaviour the analyzer will reason about, by running small, deliberate experiments and writing down what actually happened, not what documentation suggests.
  2. Build and verify the data layer: a local cluster plus a trimmed Prometheus stack, and prove that every metric the planned rules (R001–R005) depend on really exists and behaves as expected.

Prometheus was installed at the end of Phase 1 on purpose (decision taken 2026-09-24): rightsizing rules need days of history, so the history clock should start as early as possible, while later phases are being built.

4. The kind cluster

What kind does. kind ("Kubernetes in Docker") starts a Docker container that behaves like a machine. Inside it run containerd, the kubelet and the control-plane components (API server, etcd, scheduler, controller manager), set up by kubeadm exactly as on a real node. Pods run as containers inside that container.

kind create cluster --name workload-analyzer --wait 180s
kubectl cluster-info --context kind-workload-analyzer
kubectl get nodes -o wide
kubectl get pods -A

kind prefixes the cluster name with kind- to form the kubectl context: cluster workload-analyzer → context kind-workload-analyzer, node container workload-analyzer-control-plane.

5. Lab 01 — Deployment, ReplicaSet, Pod, labels, self-healing, scaling

Concept. A Pod is one or more containers scheduled together. A ReplicaSet keeps a fixed number of identical Pods alive. A Deployment manages ReplicaSets so the pod template can be changed safely (rolling updates). Labels are key/value tags; selectors are how controllers and Services find the Pods they own.

Manifest learn/01-deployment.yaml (image registry.k8s.io/e2e-test-images/agnhost:2.53, the Kubernetes project's own test image: Alpine-based, has sh/curl, serves HTTP, no Docker Hub rate limits):

apiVersion: apps/v1
kind: Deployment
metadata: {name: web, namespace: learn, labels: {app: web}}
spec:
  replicas: 2
  selector: {matchLabels: {app: web}}      # which pods this Deployment owns
  template:
    metadata: {labels: {app: web}}         # must match the selector
    spec:
      containers:
      - name: web
        image: registry.k8s.io/e2e-test-images/agnhost:2.53
        args: ["netexec", "--http-port=8080"]
        ports: [{containerPort: 8080}]
        resources:
          requests: {cpu: 50m, memory: 32Mi}
          limits: {memory: 64Mi}

Why it matters for the analyzer. Pods are disposable: names and IPs change on every replacement, and a terminating pod stops counting toward replicas before it is gone, so pod counts can briefly exceed the replica count. Findings must be keyed by workload (Deployment), never by pod name.

6. Lab 02 — Service, EndpointSlice, rolling update, readiness vs liveness

Concept. A Service gives a stable virtual IP and DNS name to a changing set of Pods, chosen by label selector; the actual Pod IPs are listed in EndpointSlices. A readiness probe decides whether a Pod receives traffic. A liveness probe decides whether the kubelet restarts the container.

Manifest learn/02-service-probes.yaml updates the same Deployment. The probes check marker files so that a single pod can be broken on purpose (real applications would use httpGet on a health endpoint):

        command: ["/bin/sh", "-c"]
        args: ["touch /tmp/ready /tmp/alive && exec /agnhost netexec --http-port=8080"]
        readinessProbe:                      # failing → removed from Service, NOT restarted
          exec: {command: ["cat", "/tmp/ready"]}
          periodSeconds: 5
          failureThreshold: 1
        livenessProbe:                       # failing 3× → kubelet restarts the container
          exec: {command: ["cat", "/tmp/alive"]}
          periodSeconds: 5
          failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata: {name: web, namespace: learn}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 8080}]

Key finding: a liveness kill looks like a clean exit. The kubelet sent SIGTERM and the app shut down cleanly, so the recorded reason is Completed with exit code 0. kube-state-metrics reports exactly this reason. Consequences:
  • R003 (frequent restarts) must count restart increases; it cannot rely on termination reasons.
  • The cause of such a restart exists only in Events — concrete support for D-007.
  • Readiness failures cause no restarts at all; they show up as unavailable replicas.

7. Lab 03 — Requests/limits, QoS, OOM, throttling, scheduling

Concept. A request is what the scheduler reserves for a container; a limit is the ceiling the kernel enforces. Memory above the limit triggers the kernel OOM killer. CPU above the limit is throttled (paused for the rest of each 100 ms period), never killed. The QoS class is derived from how requests and limits are set and decides eviction order under node memory pressure.

Manifest learn/03-resources.yaml: seven standalone pods, all using agnhost's built-in stress (--cpus N whole CPUs, --mem-total) or pause, so no extra image was needed.

# OOM: allocates 200Mi against a 64Mi limit
    args: ["stress", "--mem-total=200Mi", "--mem-alloc-size=1Mi", "--mem-alloc-sleep=10ms"]
    resources: {requests: {cpu: 50m, memory: 64Mi}, limits: {memory: 64Mi}}
# Throttling: wants 1 full CPU, limit allows 200m
    args: ["stress", "--cpus=1"]
    resources: {requests: {cpu: 100m, memory: 32Mi}, limits: {cpu: 200m, memory: 64Mi}}
# Pending 1: requests more CPU than the node has
    resources: {requests: {cpu: "64"}}
# Pending 2: requires a node label that does not exist
  nodeSelector: {disktype: ssd}

Why it matters for the analyzer.
  • A real OOM is reliably recorded as OOMKilled / 137 — unlike a liveness kill (Completed / 0). R004's main signal works.
  • The throttling ratio from the kernel's cgroup counters is exactly what the Prometheus metrics expose; 100% throttling means the workload needs more CPU than allowed — R001 must never recommend shrinking it.
  • Scheduling reasons exist only in Events; "requested" totals must exclude Pending pods.

8. Lab 04 — ConfigMap, Secret, RBAC

Concept. A ConfigMap holds non-secret configuration; a Secret holds sensitive values. Both can be injected as environment variables or mounted as files. RBAC grants verbs (get, list, watch, create, delete …) on resources to identities such as ServiceAccounts, through Roles/ClusterRoles and their bindings.

The Secret was created by command so no value ever reached git:

kubectl -n learn create secret generic web-secret --from-literal=api-token="$(openssl rand -hex 8)"

Manifest learn/04-config-secret-rbac.yaml contains a ConfigMap, a pod with three env variables (a literal value on purpose, a ConfigMap reference, a Secret reference) and a mounted ConfigMap, plus the real D-007 RBAC:

kind: ClusterRole
metadata: {name: analyzer-readonly}
rules:
- apiGroups: [""]
  resources: [namespaces, nodes, events]
  verbs: [get, list, watch]
- apiGroups: ["apps"]
  resources: [deployments, replicasets, statefulsets, daemonsets]
  verbs: [get, list, watch]
- apiGroups: ["autoscaling"]
  resources: [horizontalpodautoscalers]
  verbs: [get, list, watch]
- apiGroups: ["events.k8s.io"]
  resources: [events]
  verbs: [get, list, watch]

Testing pitfall found. The first token test wrongly showed pods and secrets as readable. kubectl still loaded the kubeconfig, sent the admin client certificate along with the token, and the API server authenticated the request as admin. Why it matters. Read access to pods exposes literal env values, which often contain secrets. This is why D-007 grants no pods access. The D-007 ClusterRole was verified exactly as designed.

10. Lab 05 — HPA and the request/utilization coupling

Concept. The HorizontalPodAutoscaler computes desiredReplicas = ceil(currentReplicas × currentUtilization / targetUtilization), with a 10% tolerance and a 5-minute scale-down stabilization window by default. For type: Utilization targets, utilization is measured as a percentage of the request. So changing a request changes utilization — and the replica count. VERIFIED (kubernetes.io)

Manifest learn/05-hpa.yaml: Deployment hpa-demo using registry.k8s.io/e2e-test-images/resource-consumer:1.15.0 (the image Kubernetes' own HPA tests use), a Service, an HPA (min 1, max 5, target 70% CPU), and a load pod that sends 3 × POST /ConsumeCPU?millicores=100&durationSec=30 every 30 s through the Service — about 300m total, shared across replicas like real traffic.

Key finding. Cutting the per-pod request on an HPA-managed workload increased total allocation. R001 must therefore emit an "HPA-coupled" caveat plus the HPA-neutral request (usage ÷ target = 300m ÷ 0.7 ≈ 430m), never a plain resize. A snapshot showed per-pod usage 190m / 0m / 1m: with few requests, random Service routing leaves some pods idle — use workload-level aggregates for HPA-managed workloads.

Note: the pre-run prediction was "2 replicas". That was an arithmetic error (150/70 = 2.14 → 3); the HPA followed its formula exactly.

Three rules for writing queries, learned here.
  1. Absent series ≠ missing data. For state metrics (waiting reason, unschedulable, HPA, throttling) no series means "condition not present". For usage metrics, no series means missing data → R005 insufficient.
  2. Filter container!="": cAdvisor adds a pod-level series next to each container series.
  3. Use range queries for short states (max_over_time): an instant query can fall between restarts.
