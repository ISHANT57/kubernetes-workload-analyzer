1. What Phase 6 was for

The dashboard (Phase 5) shows evidence numbers but not raw historical series beyond the one uPlot chart on Finding Detail. Grafana already has that (D-002: "Grafana remains for raw time-series investigation"). Phase 6's job was narrow: give resource findings and the Workloads page a direct link into Grafana's own bundled dashboard, pre-filtered to the exact workload — not build a second charting surface. Done condition (PHASES.md): each resource finding links to its panel.

2. Why no backend change was needed

A Grafana deep link is a URL, not a query result — it can be built entirely from data the frontend already has (namespace, workload name, kind) plus the Grafana base URL. Built entirely client-side in frontend/src/grafana.ts, with no backend endpoint added.

3. Confirming the dashboard and its variables via the real Grafana API

kube-prometheus-stack ships a bundled "Kubernetes / Compute Resources / Workload" dashboard. Rather than guessing its UID and template-variable names from memory, both were confirmed against the real running Grafana's API before being hardcoded into grafana.ts — the dashboard's UID and its namespace/ type/workload template variables.

4. What links where

SourceLink target
R001/R002 findings (Finding Detail)the bundled Workload dashboard, pre-filtered to that exact namespace + workload + type via template variables
Workloads pagesame dashboard, filtered per row

Health findings (R003/R004) do not get a Grafana link — a restart/OOM event is a discrete fact already shown in the finding's own evidence, not something better explained by a raw time series panel.

5. Security posture kept unchanged

Grafana's existing login requirement is left as-is — no anonymous-access change was made to enable the link. This matches the threat model's read-only/least-privilege posture (docs/threat-model.md: "Unauthorized dashboard access... Auth is required before any non-local exposure"); the link simply opens Grafana's normal login-gated URL in a new tab.
